# Microsoft 备用邮箱绑定流程

微软的保护帐户页面可能先展示说明页，页面只有“添加电子邮件”按钮；邮箱输入框不会在此阶段挂载。

绑定流程按以下顺序处理：

1. 检测保护帐户页。
2. 若尚未出现 `#EmailAddress`，点击“添加电子邮件”（同时支持 `Add email`、`Add an email` 和 `Add email address`）。
3. 等待邮箱输入框 `#EmailAddress` 出现，填入临时邮箱并点击下一步。
4. 等待 `#iOttText` 验证码输入框，轮询临时邮箱并提交 OTP。

如果页面已经直接提供 `#EmailAddress`，则跳过第 2 步，兼容旧版页面。

新版 Fluent 页面补充：邮箱表单可能使用动态 input 且提交按钮仍显示“添加电子邮件”，流程会在前置按钮后扫描可见输入框，用键盘事件写入并校验值，再点击该按钮。提交后若跳转到 `/proofs/Verify`，会按已绑定地址点击“发送电子邮件”，再识别 6 格代码框完成二次验证码；六格输入只有在 DOM 值完整匹配且页面离开代码页后才算成功，避免输入框被清空时误判。

## 临时邮箱地址策略

绑定时将目标 Outlook 邮箱的本地部分作为临时邮箱前缀。自托管 provider 的建箱顺序为：

1. 尝试创建同前缀、配置域名的邮箱。
2. 若 API 返回 `409`（地址已占用），列出当前 API 账号下的邮箱，找到同地址后验证收件箱可读性；可读则直接复用其 `mailbox_id`。
3. 找不到或无法读取时，才生成 `tm` 开头的随机邮箱作为兜底。

复用已有邮箱时会记录复用前的旧 OTP，等待新验证码期间跳过旧码，避免服务端返回历史“最新码”导致微软提示代码无效。自托管服务的 `/otp/latest` 只作为邮件索引使用，客户端会按 `email_id` 读取邮件详情并从正文的“安全代码/验证码”上下文解析；这是为了避开服务端把 HTML 隐私链接编号误报为 OTP 的情况。邮件时间戳的小数位也会标准化后再参与发码时间过滤。

运行环境若设置了 HTTP/SOCKS 代理，浏览器本地 CDP 的 `127.0.0.1`/`localhost` 控制连接会自动加入 `NO_PROXY`，外部 OAuth 和邮件请求仍按原代理配置执行。
